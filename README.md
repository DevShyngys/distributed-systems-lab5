# Лабораторная работа 5 — обнаружение отказа и чтение с реплики

CSS4004 «Распределённые системы». Продолжение ЛР 4. Сервис заказов читает
товар сначала у основного каталога с таймаутом **1 секунда**, а при неудаче
переключается на реплику и продолжает работать.

| Узел | Файл | Порт | Роль |
| --- | --- | --- | --- |
| Catalog Primary | `catalog_service.py --role primary` | 5001 | Основной источник данных |
| Catalog Replica | `catalog_service.py --role replica` | 5002 | Копия только для чтения |
| Order Service | `order_service.py` | 5003 | Читает основной узел, при ошибке — реплику |

**Таймаут обращения заказов к основному узлу: 1,0 с** (ключ `--timeout`).
Таймаут обращения к реплике: 2,0 с.

Начальное состояние обоих каталогов:

```json
{"id": 1, "name": "Laptop", "price": 500000, "stock": 10, "version": 1}
```

## Установка

```bash
python3 -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

## Команды запуска

Каждая — в своём терминале.

```bash
# 1. реплика
python3 catalog_service.py --role replica --port 5002

# 2. основной каталог
python3 catalog_service.py --role primary --port 5001 \
        --replica-url http://127.0.0.1:5002 --replica-delay 5

# 3. сервис заказов (таймаут к основному узлу — 1 секунда)
python3 order_service.py --port 5003 \
        --primary-url http://127.0.0.1:5001 \
        --replica-url http://127.0.0.1:5002 \
        --timeout 1.0
```

Автоматический прогон всех пяти экспериментов:

```bash
python3 run_experiments.py
```

Скрипт сам поднимает три процесса, останавливает и перезапускает основной
узел, замедляет его ответы и печатает таблицу результатов. Полный вывод —
в `experiments_output.txt`, объединённый журнал трёх сервисов —
в `combined_log.txt`.

## Эндпоинты

### Каталог (оба узла)

| Метод и адрес | Назначение |
| --- | --- |
| `GET /health` | роль узла, версии товаров, текущая задержка ответа |
| `GET /products/<id>` | состояние товара на этом узле |
| `PUT /products/<id>` | обновление (только основной узел), `mode`: `async` или `sync` |
| `POST /admin/response-delay` | задать задержку ответа на чтение, тело `{"seconds": 3}` |
| `POST /internal/replicate` | приём новой версии (только реплика), отвечает ACK |

Реплика остаётся только для чтения: `PUT` на ней возвращает 403.

### Сервис заказов

| Метод и адрес | Назначение |
| --- | --- |
| `POST /orders` | заказ, тело `{"product_id": 1, "quantity": 1}` |
| `GET /orders/<id>` | сохранённый заказ |
| `GET /catalog-status` | опрос `/health` обоих узлов |
| `GET /health` | адреса узлов и значения таймаутов |

Ответ на создание заказа содержит `catalog_source` и `catalog_version`, а при
переключении — ещё и `fallback_reason`:

```json
{
  "order_id": 104,
  "product_id": 1,
  "name": "Laptop",
  "price": 450000,
  "stock": 10,
  "quantity": 1,
  "total": 450000,
  "catalog_source": "replica",
  "catalog_version": 2,
  "fallback_reason": "нет ответа за 1.0 с (таймаут)"
}
```

## Результаты пяти экспериментов

| Эксперимент | Catalog Primary | Источник заказа | Версия | Результат |
| --- | --- | --- | --- | --- |
| 1. Нормальная работа | работает | primary | 2 | актуальные данные |
| 2. Узел остановлен | не отвечает | replica | 2 | чтение продолжается |
| 3. Узел восстановлен | работает | primary | 2 | возврат к основному |
| 4. Медленный узел | задержка 3 с | replica | 2 | ложное подозрение |
| 5. Отставание реплики | остановлен | replica | 2 | старая цена 450000 |

### Эксперимент 1. Нормальная работа

```json
{"order_id": 101, "catalog_source": "primary", "catalog_version": 2}
```

### Эксперимент 2. Основной узел остановлен

```json
{"order_id": 102, "catalog_source": "replica", "catalog_version": 2,
 "fallback_reason": "нет соединения (сервис не запущен)"}
```

Журнал:

```
[ORDERS ] PRIMARY не ответил (нет соединения (сервис не запущен)) — перехожу на РЕПЛИКУ
[REPLICA] Чтение товара id=1 → version=2, price=450000, stock=10
[ORDERS ] Заказ order_id=102 создан: источник replica, version=2, price=450000
```

### Эксперимент 3. Восстановление

Данные хранятся в памяти, поэтому перезапущенный узел стартовал бы пустым.
Он забирает актуальное состояние с реплики ключом `--sync-from`:

```
[PRIMARY] Узел primary запущен на 127.0.0.1:5001
[PRIMARY] Восстановлено записей с http://127.0.0.1:5002: 1
[ORDERS ] Чтение товара id=1: ответил PRIMARY, version=2
[ORDERS ] Заказ order_id=103 создан: источник primary, version=2
```

В реальной системе восстановление идёт из журнала транзакций или от другой
реплики — здесь показан тот же принцип в простейшем виде.

### Эксперимент 4. Медленный основной узел

Узел **запущен и исправен**, но отвечает за 3 секунды при таймауте 1 секунда:

```bash
curl -X POST http://127.0.0.1:5001/admin/response-delay \
     -H 'Content-Type: application/json' -d '{"seconds": 3}'
```

```
[PRIMARY] Чтение задержано на 3.0 с (имитация перегрузки)
[ORDERS ] PRIMARY не ответил (нет ответа за 1.0 с (таймаут)) — перехожу на РЕПЛИКУ
[ORDERS ] Заказ order_id=104 создан: источник replica, причина: нет ответа за 1.0 с (таймаут)
```

Заказ был создан за 1022 мс: ровно секунда ожидания основного узла плюс
быстрый ответ реплики. Сам основной узел при этом продолжал работать и через
две секунды честно обработал запрос — его ответ просто уже никому не был нужен.

### Эксперимент 5. Отстающая реплика

Цена меняется с 450000 на 400000 в асинхронном режиме (доставка через 5 с),
основной узел останавливается **до** доставки:

```
[PRIMARY] ОБНОВЛЕНИЕ id=1 принято: {'price': 400000} → version=3, режим async
[PRIMARY] SUCCESS отправлен клиенту НЕ дожидаясь реплики (async)
[PRIMARY] АСИНХРОННО: доставка version=3 начнётся через 5 с
            ← здесь основной узел остановлен
[ORDERS ] PRIMARY не ответил (нет соединения) — перехожу на РЕПЛИКУ
[ORDERS ] Заказ order_id=105 создан: источник replica, version=2, price=450000
```

Заказ оформлен по старой цене 450000, хотя товар уже стоил 400000. Версия 3
до реплики не доехала и уже не доедет: узел, который её хранил, остановлен.

## Ответы на вопросы защиты

**Почему сервис заказов переключился на реплику?**
Потому что обращение к основному узлу завершилось неудачей раньше, чем истёк
таймаут ожидания ответа: либо соединение не установилось (процесс не запущен),
либо ответ не пришёл за 1 секунду. Любой из этих исходов считается отказом, и
чтение повторяется с реплики — она доступна только для чтения, но этого
достаточно, чтобы оформить заказ.

**Доказывает ли таймаут, что основной узел остановился?**
Нет. Таймаут означает только одно: ответ не пришёл за отведённое время.
Причин может быть несколько — процесс остановлен, перегружен, занят долгой
операцией, или ответ потерялся в сети. Эксперимент 4 показывает это прямо:
узел работал и в итоге обработал запрос, но сервис заказов уже счёл его
отказавшим. Отличить «медленный» от «мёртвого» по одному таймауту
принципиально невозможно; это известная проблема обнаружения отказов в
асинхронных системах. Таймаут даёт подозрение, а не доказательство.

**Почему реплика может вернуть старую цену?**
Потому что обновления доходят до неё не мгновенно. В асинхронном режиме
основной узел отвечает SUCCESS сразу после записи у себя, а доставку копии
выполняет позже. В промежутке на узлах лежат разные версии одной записи, и
чтение с реплики возвращает устаревшую. Если основной узел остановится до
доставки, как в эксперименте 5, изменение вообще не доедет — и будет потеряно.

**Что даёт переключение на реплику и в чём его ограничение?**
Даёт доступность: система продолжает обслуживать чтение, когда основной узел
недоступен — заказы оформляются, а не падают с ошибкой.

Ограничений три. Во-первых, данные могут быть устаревшими: доступность
получена ценой согласованности. Во-вторых, реплика работает только на чтение,
поэтому обновления во время отказа невозможны. В-третьих, решение о
переключении принимается по таймауту, то есть по догадке — возможно ложное
срабатывание на медленном, но живом узле, что создаёт лишнюю нагрузку на
реплику именно тогда, когда основной узел и так перегружен.
